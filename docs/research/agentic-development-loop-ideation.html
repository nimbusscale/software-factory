Agentic Development Loop

How an issue gets from "ready" to merged with very little human time, and what has to be true for that to work. These notes come from building road-trip-agent, and they are the starting point for a new project built to try this out.

Nothing here is final. Everything came from one brainstorming session. Later discussions or implementation may change, adjust or drop any item, including those marked Direction.

  • DirectionThe concept made sense in the first brainstorm. The details are not decided.
  • Starting guessA sensible first choice, to tune with real runs.
  • OpenNeeds more thought, or a real run, to settle.

The goal

  • People spend their time on design. Most human work is talking through features, functions and standards. Issues hold the result of those talks, cut down so a fresh agent can do the work.
  • Moving an issue to Ready starts the work. Nobody has to open a session or say "please do this issue". This applies only to issues with the auto-develop label.
  • Trust grows over time. People stay close while the foundation and controls are new, and step back as the controls prove themselves.
  • The loop is generic. The aim is one workflow that any project can use. Each project brings its own docs and rubric.

How it runs

Direction This is a workflow. The steps are known up front. Code follows them and calls a model only where judgment is needed. Anthropic's "Building Effective Agents" article calls this a workflow. The inner loop is what it calls evaluator-optimizer: one model does the work, another judges it, and the two repeat.

Rough sketch of the inner loop
for round in 1 to n:                    # n is set per project, default 3
    findings = run code reviewers       # new session each round
    run implementer with findings       # resumes its session
    run acceptance checks               # failed names go into the next findings
    answer = drift checker: "Is the approach still right?"
    if answer is no: end this attempt
open the PR
  • Direction The workflow is an Agent SDK application. Rounds, counters, stop rules and checked JSON are too much logic for shell commands around claude -p, the same way a bash pipeline grows into a real program. The SDK still runs Claude Code underneath.
  • Direction The workflow starts every role itself, with no subagents. Each role is its own SDK call with its own system prompt. The implementer resumes its session to keep its context. Code reviewers get a new session each round, so they start fresh.
  • Direction Every role finishes with a tool call. The role hands back its results through a finish tool, such as a code reviewer's findings. The tool's schema checks them, and a Stop hook won't let the role end until it has made that call.
  • Direction The workflow picks the path, and agents work inside each step. Each role hands back data, and the workflow reads it to choose between branches already written in the code. For example, if the drift checker answers no, the workflow ends the attempt. A model can't add a step or skip one. Inside a step, the agent decides how to do the work, such as which files to read and how to make the change.
  • Open How to handle a wrong approach. More findings to the same implementer won't fix a wrong approach. A separate drift checker could catch it, or a finding type from the purpose reviewer. What happens next is open too. One option treats it like a crash: restart the implementation with guidance not to repeat that approach, and count it as an attempt. It would then reach you only when the attempts run out. A wrong approach can come from the implementer or from the issue. An implementer can misread a doc on a good issue, and a fresh attempt often fixes that. When the issue itself is wrong, no retry helps. To start, the drift checker says which cause it thinks it is, and every case still retries the same way. That record also shows whether issue prep or the implementer needs work. If retries never fix a wrong issue, those cases go straight to Needs attention instead. Real runs will show what works.
  • Open Where the workflow asks a model for a judgment. Some steps exist to answer a question that the workflow then acts on. The issue checker asks whether an issue is ready to start. The drift checker asks whether the overall approach is still right. The decision reviewer and the merge decision are others. It's also open whether a judgment can do more than say yes or no. For example, the drift checker might first steer the implementer back on track, and end the attempt only if that fails.
  • Open Whether a judgment remembers its earlier calls. Each call could start fresh, or it could know what it said before on the same issue. This matters most when a call can act more than once. If the drift checker steers the implementer and the work drifts again, the drift checker needs to know it already tried. A restarted implementer also needs to know which approach failed, so it doesn't repeat it.

Code review inside the loop

This answers "is the code right?" It happens before the PR opens, so CI doesn't need a second code review.

  • Starting guess A set number of rounds, every time. Each round is a review, then a fix. The loop always runs n rounds, with no early stop. n is set per project, and defaults to 3. The last fix goes straight to the PR, with no code review after it.
  • Direction Later rounds review only what the fixes changed. Round one reviews the whole PR. Each later round reviews only the changes since the last review, plus the list of earlier findings. That keeps a fix from pulling more of the code base into review.
  • Direction The implementer fixes every finding it gets. It doesn't judge whether a finding is worth fixing.
  • Open A finding check. Many findings don't hold up (see evidence). A small agent could check each finding before it reaches the implementer, and drop the ones that are wrong or not worth fixing.
  • Direction The simplifier runs once. Running it every round means it keeps picking at the fixes. The code reviewers then see the final code.
  • Direction Code runs the rounds, and models make the judgment calls. A model can skip a step or stop early, so the round count belongs in code.
  • Direction Use stock parts where we can. The quality reviewer can be something stock. The purpose reviewer gets its project knowledge from the issue and docs, so its own prompt can stay short and work on any project.
  • Starting guess Two code reviewers side by side. The quality reviewer checks fit for use: is the code good? It looks for bugs, and also at reuse, simplification, efficiency and conventions. The purpose reviewer checks fit for purpose: does the work do what was asked? It goes through each acceptance criterion in the issue and answers yes or no, and any no is a finding. It also flags work that ignores the project's design or architecture. Good code can still miss what the issue asked for, so both are needed. Separate runs also find different problems.
  • Direction Code review checks the tests. A reviewer judges whether the tests cover the hard logic, and flags tests that only restate the code. For example, a test that checks a setting equals its default value is a finding.
  • Open Whether to measure coverage. Coverage is easy to game, especially by agents. It might help next to the test review, as a way to spot untested code, but not as a target to hit.
  • Open Where test review lives. In the stock quality reviewer if it covers tests. Otherwise in the purpose reviewer, or in a small reviewer of its own.

Acceptance checks

Agents game checks they can see. In one study, a model gamed the tests in over half its tasks. Making the tests read-only didn't stop it, and hiding them almost did.

  • Direction Some checks are hidden from the agents. The issue lists its acceptance criteria in plain words, which you agree on during planning. The main session turns them into checks that test from the outside, through the project's commands, API or files, never its internals.
  • Direction They live in a separate private repo. Only CI or the workflow's code can fetch it, with a token no agent gets.
  • Direction Controls keep the implementer from seeing them. Which controls is decided during implementation.
  • Direction The workflow runs them every round. After each fix, the workflow's code runs the checks. No agent runs them. The names of any failed checks go into the next round's findings, so the implementer learns early that it's missing the mark.
  • Direction The implementer only learns which checks failed. It's told their plain-language names, which say nothing the issue didn't.
  • Direction CI runs them again as the final gate. A failure there is a send-back to Ready and uses an attempt.
  • Open Who checks the checks. A hidden check can be wrong too.

Decision review

This answers "what's new here?" It looks for choices in the work that no doc or existing pattern settles, and reports them to a person. It doesn't check code quality or whether the work meets the issue, because the code reviewers do that. A small decision rubric drives it.

  • Direction It runs once in CI, over the whole PR. It reads the diff, the issue, the docs and the decision rubric. It never sees the implementer's reasons, so it can't be talked into accepting a choice.
  • Direction It finds the decisions itself. The implementer doesn't keep a decision list. What counts as a decision gets tuned in one place, the decision rubric, instead of in every implementer run.
  • Direction Only new decisions count. A decision is a choice between options that no doc or existing pattern settles, or a choice that departs from one. Following an established pattern isn't one. For example, keeping trip drafts in memory instead of the database, when nothing says where drafts live, is a decision. Using the validation library the docs already require is not.
  • Direction It reports, and doesn't judge. Each decision it finds gets one PR label: new, because no doc covers it, or conflicting with a doc, which it names (see Labels). The report goes on the PR for a person, and there are no send-backs. Code reads the flags, and any flag holds the PR in Waiting to merge.

Direction Accepted decisions become patterns. When a person accepts a new decision, usually in an interactive session, the doc update goes into the same PR. The rule then lands together with its first use, and later work follows it instead of inventing its own. Over time this builds the project's library of patterns.

Merging

The merge decision is code. It reads the CI results, the hard limits and the decision reviewer's flags, and makes no judgment of its own. The judgment happens earlier, in the code reviewers, the drift checker and the decision reviewer.

Direction A PR merges on its own only if all of these hold:

  • CI passes, including the acceptance checks.
  • The decision reviewer flags nothing.
  • No protected files changed, such as config, CI or security-sensitive files.
  • The issue has no human-review label. You set this label during planning for important work.

Direction Protected files need a logged reason. A hook denies the first edit to a protected file until the agent logs why with a tool, and then the edit goes through. The agent keeps working, and the reasons go in a PR comment. This records a reason but doesn't block the change, so the PR still waits for you. The merge check also compares the diff with the logged reasons, because a shell command can change a file without passing through the hook.

Direction Start tight. Early on, every PR waits for you. Remove limits as the merge decisions prove good.

Direction Every PR tests the merge decision. A setting says whether the workflow may merge on its own. While it's off, the workflow still makes its decision and posts it on the PR: ready to merge or not, why, and how the acceptance criteria were met. You mark each decision as good or not good, and when it's not good, you label why. Those labels are the data for tuning, and the share of good decisions is the measure to track. How exactly this works is something to try out.

Direction Stay informed. A regular summary lists merged work and its decisions. That's how you'd notice the project drifting.

Risks to keep in view

  • If merging deploys, an automatic merge is also an automatic deploy.
  • On a public repo, agents must only read issue and PR text from your account. Otherwise a stranger's comment could steer an agent that can push code.
  • The reviewers lean on the docs. If a wrong doc was rubber-stamped, they enforce the wrong thing.

When things go wrong

Direction One attempt counter per issue, kept in code. Every crash or send-back adds one. That single counter covers every route back into the loop, so no combination of routes can run forever. It's saved outside the run, so a workflow that dies doesn't lose the count. When the counter reaches 3 Starting guess, the issue goes to Needs attention instead of Ready, with each attempt's reason in the issue.

Direction One way back. Anything sent back goes to Ready, with its reason in the issue, and runs the full flow again. The next run continues from the existing branch and PR. Four things send an issue back: the run crashes, the workflow ends the attempt, acceptance checks fail in CI, or the workflow itself dies. All four take this path, so there's no special route for each.

Direction Each attempt records why it ended. Crashed, hit its limit, stalled, acceptance checks failed, wrong approach (implementer), or wrong approach (issue). When the issue comes to you, it lists every attempt and its reason.

Direction Limits end attempts that go nowhere. Agents get confused and go in circles, and that's hard to detect while it happens. So each role has a cap on turns and cost, and reaching it ends the attempt with "hit its limit" as the reason. More rarely, an agent stops producing any output. The workflow stops an agent that has been silent for a set time, and records it as "stalled".

Direction Work nobody owns goes back to Ready. The stall check can't help if the workflow itself dies, because nothing is left to move the issue. So something outside that run has to find issues in In development that no running workflow owns, and move them back to Ready.

Open How orphaned work is found. For example, each time the workflow looks for work, it could also look for issues it doesn't own in In development. The Symphony spec on the reading list handles this.

The loop must save its stage and findings outside the session, or the next run won't know where things stood.

Integration and release Open

A real project may need its own loop after merge: deploy to staging, run integration tests, and hold the release if they fail. CI and CD would separate, and versions would matter. This is best learned by building it.

Human pipelines have a few patterns that agents could copy:

  • Open a new bug issue linked to the original. This is the current lean, because the fix comes in the same way as all other work and needs no new machinery.
  • Revert the change and reopen the issue.
  • Hold the release until a fix lands.

Two things need care. A release can hold several changes, so something has to work out which one caused the failure. A new issue also starts a new attempt counter, so the link matters: two bugs on the same change should come to you.

Loading skills

Direction Load skills the same way every time, and don't leave it to the agent to pick them up. Each role lists the skills it needs. The workflow reads those skill files and joins them into that role's system prompt.

  • A missing skill stops the run. The workflow reads the files itself, so a missing file is an error.
  • A skill goes in as plain text. $ARGUMENTS isn't filled in, and supporting files need real paths.

## Where to save what you learn

Before saving a memory, ask: would an agent that never talks to me need this to do its work?

- Yes, and it's a lasting rule or decision: it goes in a repo doc. Propose the change, and don't save it as a memory.
- Yes, but it's about one piece of work: it goes in that issue.
- No, it's only about how this session works with me: save it as a memory.
- The repo already says it: save nothing.

If you can't tell, ask me. Never choose memory because it's quicker than changing a doc.
  • Direction Only the main session writes memory. Workers report what they learned in the PR, and you or the main session decide what's kept. That stops one agent's bad note from spreading.
  • Direction Reviewers get fresh eyes. They get documents and code, with no memory. Intent helps a reviewer, and the implementer's reasons make it more likely to accept a shortcut. Documents mostly hold intent. Memory and chat mix the two.
  • Direction Rules about talking to you move to the repo. They count as memory only while the main session is the one talking to you. An agent writing to a PR or to Slack needs them too.
  • Direction Workflow agents see only what the repo gives them. Each role's setup is defined in code: its prompt, its tools, and the repo's CLAUDE.md and skills. User files such as Claude Code's memory, ~/.claude/CLAUDE.md and ~/.claude/skills are left out, even on the same machine. Anything an agent needs goes in the repo. Only the main session uses a person's own files.
  • Open Sharing memory with other agents. The main session could write memory and other agents could read it, wherever they run. A tool built for shared memory is one way to do that. We don't plan to do this in the new project, but it isn't ruled out. Reviewers would still go without it, to keep their fresh eyes.

Agents are the main readers of project docs, and English is how they get programmed. So docs need systems around them for quality, consistency and style, as code does. The systems differ, but the care should match.

Writing rules to start from

  • Write the doc as if it was always this way. Nobody needs to know what an earlier draft said.
  • Keep reasons, and drop history. Git and the issue already hold the history.
  • Default to the issue. Only rules that apply beyond one change go in the docs.
  • Keep the decision rubric short enough that you read every change. It's the one document where rubber-stamping does the most harm.

Evidence so far

All of this comes from road-trip-agent. It's one project with small samples, and some counts are rough. Treat it as a starting point.

Reading before building

These show how others handled the same problems. They're for reference and ideas only, not designs or guides to follow. We may use parts of them, change them, or decide they don't fit.

  • Before building how the workflow claims, retries and stops work on issues: the Symphony spec, for its issue states, retry delays and stall check.
  • Before settling the inner loop's rounds: Stripe's Minions posts, for a fixed workflow with agent steps and a cap of two CI rounds before a person takes over.
  • Before organizing the docs or building the doc curator: OpenAI's harness engineering post, for its short map document and its doc gardening agent.
  • Before designing integration and release: two cases where automatic merging went wrong. In one, an agent PR silently undid another merged two hours earlier. In another, an automatic revert stalled because GitHub doesn't let a PR's author approve it.

Open questions

  • Decision reviewer quality. Can a reviewer with only docs match a session with memory? One test is to run it on old PRs and compare its flags with the decisions you actually questioned.
  • The inner loop. What n should default to. This needs real runs.
  • Which stock quality reviewer. Read the current /code-review prompt, look at third-party review skills, and pick one. The built-in /code-review has no skill file to join into a prompt, so it would run as its own call, with its own output format.
  • A reviewer on another model. Not part of the first version. Supporting other models could be an option added later. Run them on the same PRs as the Claude reviewer, to see whether they give a better review or find different problems.
  • Judgment calls. Which model calls the workflow needs, and at what points. See How it runs.
  • The trigger. Polling or an event from the issue tracker.
  • Talking to you. GitHub stays the record. A one-way nudge with a link is the likely way to get your attention, sent only when work has stopped until you act. A two-way channel like Slack or Discord is harder, because replies have to end up in the issue, where the next run and other agents can read them. Also open: how you'd get notified and give permission while a headless agent is working. That may need a spike.
  • Sharing rules across projects. Each repo could copy them, or they could live in a shared file or plugin.
  • Hard limits. Which files are protected, and which limits come off first. Whether docs that hold rules need protecting too, because a doc change could justify a shortcut.
  • Limits by kind of change. Which kinds of change can merge on their own, judged by code from the paths a PR changes. The repo may need organizing so that its paths match those kinds.
  • Doc controls. The style guide, and the rubric for what belongs in docs. Which of its checks, if any, can move into code. How often the doc curator runs, and whether its issues go to Triage or straight to Ready.
  • Integration. See Integration and release.
